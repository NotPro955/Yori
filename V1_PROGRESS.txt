Yori V1 Security/Privacy Prototype Progress
===========================================

Scope
-----
This is a security-focused academic/prototype P2P chat system. V1 does not attempt
to become Tor, Signal, a production anonymity network, a DHT, a mixnet, or a global
traffic-analysis defense.

Repository layout
-----------------
- client/: terminal client, direct peer listener, crypto/session/message/onion logic
- server/: coordination/presence server, heartbeat server, final delivery endpoint
- Both directories are independent Go modules.
- The repository root has no go.mod; Go commands must run separately in client/ and server/.
- go.work describes both modules for tooling convenience.

Current status
--------------
All phases are complete and validated. The following is a full inventory of what is
implemented, tested, and verified across both modules.

Phase 1 - Protocol and transport (COMPLETE)
--------------------------------------------
- Protocol version 1 enforced on every packet (client and server).
- Every outgoing packet gets a cryptographically random 16-byte base64 packet ID.
- Circuit IDs assigned per onion route; carried through each relay hop.
- TTL field present on every packet; max is 8, default is 5.
- Packet payload capped at 48 KB; full packet capped at 64 KB.
- Recipient (To) field capped at 32 bytes.
- bufio.Scanner buffer bounded to maxPacketBytes on all readers (client and server).
- Read deadlines: 15 s at registration, 5 min during session (server); 15 s on peer
  connections and heartbeat connections.
- Write deadlines: 15 s on server writes; 5 s on direct peer TCP sends.
- Packet type allowlist enforced on both sides; unknown types are rejected.
- validatePacket() called on every inbound packet before processing.
- Direct peer TCP proxy: each relay opens a new TCP connection per hop.
- Onion envelopes with per-hop AES-GCM encrypted layers.
- Route selection excludes sender and recipient; 2 to 5 relays chosen.
- TTL decremented at each relay; packet dropped when TTL reaches 0 on a non-exit hop.
- Bounded relay jitter: 50-500 ms using crypto/rand.

Phase 2/3 - Cryptography and authenticated sessions (COMPLETE)
---------------------------------------------------------------
- X25519 ECDH key agreement for both session keys and onion layer keys.
- HKDF-SHA256 replaces raw SHA-256; all key derivation uses HKDF.
- Session key label: "yori/session/v1".
- Directional keys:
    send = HKDF(.., "yori/session/v1/<sessionID>/a-to-b")
    recv = HKDF(.., "yori/session/v1/<sessionID>/b-to-a")
  Initiator uses a-to-b as send key; responder flips.
- AES-256-GCM with random 12-byte nonce prepended to ciphertext (base64 encoded).
- Separate AAD context strings per use case:
    session offer:  "yori/session/v1/offer"
    session reply:  "yori/session/v1/reply"
    onion layer:    "yori/onion/v1"
    chat message:   "yori/message/v1|<sessionID>"
- In-memory Ed25519 identity key generated at startup via crypto/rand.
- Session offers and replies carry an Ed25519 signature binding sender + sessionID +
  ephemeralPublicKey under label "yori/session/v1|<sender>|<sessionID>|<pubKey>".
- Signature verified on receipt using the peer's identity key from the server peer record.
- Identity fingerprint: SHA-256(identityPublicKey), first 16 base64 characters shown.
- TOFU identity pinning: first-seen identity stored per peer; changes set keyChanged=true
  and block new sessions (/session prints WARNING and returns early).
- Private identity and session keys are never sent to or stored on the server.
- Relay key (separate X25519 key) used only for onion layer decryption at relay hops.
- Each onion layer uses a fresh ephemeral X25519 key; relay uses its relayKey to peel.

Phase 4/5 - Onion routing and messaging (COMPLETE)
---------------------------------------------------
- buildOnion() constructs layers inside-out: innermost layer carries recipient and
  original payload; outer layers carry only next hop and opaque ciphertext.
- Each onionPacket = {ephemeral: <pubKey>, ciphertext: <AES-GCM blob>} encoded as JSON
  then base64 in Packet.Payload.
- decryptOnionLayer() uses the relay's relayKey to recover the onionEnvelope.
- Exit relay (where envelope.Next == serverAddr) sends a "deliver" packet to the server
  over its existing main TCP connection.
- Server deliver() rewrites "send" -> "message" for the recipient and forwards the opaque
  payload; the server never decrypts the chat ciphertext.
- chatEnvelope fields: Version, MessageID (random 16-byte base64), SessionID, Counter
  (monotonic uint64), Sender, Body.
- Counter starts at 1 (send count incremented before use); Counter == 0 is invalid.
- Duplicate counter check per sessionID: state.received[sessionID][counter] must be false.
- Replayed ciphertexts (same counter in same session) are rejected.
- Circuit ID logged in short form (first 8 chars) when a route is established.
- secureShuffle() uses crypto/rand Fisher-Yates for unbiased relay selection.

Phase 6/7 - Presence, reliability, and privacy hardening (COMPLETE)
---------------------------------------------------------------------
- Heartbeat runs as a separate goroutine over a separate TCP connection to port 9500.
- Client sends a JSON registration heartbeat packet first (type="heartbeat", payload=username)
  then a JSON heartbeat packet every 5 seconds (type="heartbeat").
- Server heartbeat_listener on port 9500 validates registration strictly:
  type must be "heartbeat", payload (username) must be non-empty.
- heartbeat_connection() enforces a 15 s read deadline per heartbeat packet.
- On heartbeat connection drop, server closes the corresponding main data connection,
  triggering broadcast_users() to propagate the disconnect to all peers.
- Duplicate username rejection: server checks connections[username] before registering;
  sends error packet and closes connection if already taken.
- Username validation: 3-32 characters, only [a-zA-Z0-9_-] allowed.
- broadcast_users() fires on every connect and disconnect.
- user_list() returns at most 3 peers (crypto-shuffled, excluding the requester and
  entries without a peer address or relay key).
- Server logs: print only username and packet type; no ciphertext, no socket addresses.
- directSendToUser() retries once if peer list is empty, waiting up to 2 s on the
  state.peerUpdates channel before the second attempt.
- Key material zeroed byte-by-byte in clearSession() and clearAllSessions() before map
  deletion; state.privateKey nilled to force fresh key generation next session.
- Global write mutexes (clientWriteMu, serverWriteMu) serialize concurrent writes.
- peerUpdates channel (buffered 1) signals peer-list changes to the routing layer.

Completed audit
---------------
All 10 Go files were inspected.
Original major findings:
- No protocol version, packet IDs, circuit IDs, TTL, packet size limits, or replay protection.
- Raw SHA-256 was used directly on X25519 shared secrets.
- No authenticated long-term identity keys or key-change detection.
- Session keys were not directionally separated.
- Relay selection used math/rand and could repeat/loop.
- Direct peer routing exposed peer addresses by design.
- No connection deadlines or bounded scanner buffers.
- Heartbeat mixed raw text and usernames.
- Server logs exposed ciphertext and socket addresses.
- No crypto, protocol, onion, fuzz, or reliability tests existed.

Protocol and transport:

- Added random packet IDs, circuit IDs, and TTL fields.
- Added packet payload/recipient size limits.
- Added bounded Scanner buffers for client/server packet readers.
- Added read/write deadlines on server and peer connections.
- Added packet metadata validation.
- Added direct peer TCP proxy connections; peers open a new connection for each hop.
- Added onion envelopes with per-hop encrypted layers.
- Added bounded route selection excluding sender and recipient.
- Added per-hop TTL decrementing and circuit IDs.

Cryptography and sessions:
- Replaced raw SHA-256 session derivation with HKDF-SHA256.
- Added separate directional send/receive keys.
- Added AES-GCM AAD helper functions.
- Added in-memory Ed25519 identity keys.
- Added signed ephemeral session offer/reply metadata.
- Added identity fingerprints and a /fingerprint command.
- Added in-process key-change detection and session blocking.
- Private identity/session material is not sent to the server.

Messaging:
- Added authenticated message envelopes containing protocol version, message ID, session ID, counter, sender, and body.
- Added session-context AAD.
- Added monotonic send counters.
